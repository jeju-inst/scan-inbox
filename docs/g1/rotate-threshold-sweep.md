# 회전 임계값(`--rotate-pages-threshold`) 글꼴·플랫폼별 측정

작성: 조남운 · claude/scan-inbox-worker-2 · 2026-11-16

## 배경

PR #19(Windows 실기)에서 `test_rotate_behavior_with_default_engine` 이 1건 실패했습니다. 원인은 Windows 파일 시스템이 아니라
**코퍼스 글꼴(Windows 시험 머신은 NotoSansKR, macOS 는 나눔바른고딕)에 따른 회전 임계값 민감도**였습니다. 이 문서는 macOS 에서 재현하고
글꼴 4종·임계값 5개를 잰 결과와 수정 근거입니다. 합성 코퍼스(`rotated_blank`: 빈 쪽 2·5, 이미지가 90도 회전된 3쪽, PDF `/Rotate 90` 인 4쪽,
150dpi)이며 소표본 관찰값입니다. 실스캔 일반값이 아닙니다.

## 측정 (macOS arm64, Tesseract 5.5.3, OCRmyPDF 17.13.0, tessdata_fast kor 4.1.0, `--deskew`, 재시도 끔)

각 칸은 3쪽 / 4쪽 글자 재현율(정답 대비, 공백 무시). 1.0 미만이어도 0.6 이상이면 읽을 수 있는 쪽으로 봅니다.

| 코퍼스 글꼴 | 0.5 | 0.8 | 0.9 | 1.0 | 1.2 | 어느 값이 두 쪽을 모두 살리나 |
| --- | --- | --- | --- | --- | --- | --- |
| 나눔바른고딕 Regular | 0.89 / **0.03** | 0.89 / **0.03** | 0.89 / **0.03** | 0.89 / 1.00 | 0.89 / 1.00 | 1.0 이상 |
| 나눔바른고딕 Light | 0.87 / **0.03** | 0.87 / 0.97 | 0.87 / 0.97 | 0.87 / 0.97 | 0.87 / 0.97 | 0.8 이상 |
| NotoSansKR Regular | 0.94 / **0.05** | **0.03** / 1.00 | **0.03** / 1.00 | **0.03** / 1.00 | **0.03** / 1.00 | **없음** (3쪽은 0.5 만, 4쪽은 0.8 이상만) |
| 나눔스퀘어 R | **0.05** / 0.97 | **0.05** / 0.97 | **0.05** / 0.97 | **0.05** / 0.97 | **0.05** / 0.97 | 없음(3쪽은 어느 값에서도 읽히지 않음) |

PR #19 문서의 Windows x64(Tesseract 5.4.0) 측정과 합치면 다음과 같습니다.

| 환경 · 글꼴 | 3쪽·4쪽이 모두 살아나는 단일 임계값 |
| --- | --- |
| macOS 5.5.3 · 나눔바른고딕 | 1.0 이상 |
| macOS 5.5.3 · NotoSansKR | 없음 |
| Windows 5.4.0 · NotoSansKR | 0.8~1.0 |
| Windows 5.4.0 · 맑은 고딕 | 0.5·0.9 에서 정상(1.2 에서는 3쪽이 쓰레기) |

**어떤 값을 골라도 글꼴·Tesseract 버전이 바뀌면 깨집니다.** 또한 1.2→0.5 재시도 구조는 NotoSansKR(macOS)에서 첫 실행은 3쪽,
재시도는 4쪽이 깨져 "문제 쪽 수가 같아" 어느 쪽을 채택해도 한 쪽이 쓰레기였습니다.

## 추가로 드러난 판정 결함

NotoSansKR 0.5 출력의 4쪽(쓰레기)은 한글 비율 0.13·짧은 조각 비율 0.55 인데 `suspect_pages` 의 한글 비율 상한이 0.1 이라 놓쳤습니다
(의심 판정이 없으니 재시도·병합도 시작되지 않음). 쓰레기 쪽들의 한글 비율은 0.03~0.13, 정상 한글 쪽은 0.85 이상, 영문 쪽이 섞인 묶음은
한글 비율은 낮지만 짧은 조각 비율이 0.2 미만이라 상한을 0.2 로 올려도 오탐하지 않았습니다(단위 시험으로 고정).

## 수정

단일 값 대신 **쪽 단위 병합**을 추가했습니다(후보 (1) 임계값 추가 · (2) 글꼴 고정 · (3) 판정 강화 중 (3)을 필요 조건으로 하고, (1)·(2)는 택하지 않음).

1. `suspect_pages` 한글 비율 상한 0.1 → 0.2 (위 결함).
2. 재시도 후에도 의심 쪽이 남으면, 시도별 OCRmyPDF 출력에서 그 쪽을 **읽을 수 있는 시도의 쪽으로 바꿔 끼운 PDF** 를 pypdf 로 만들고
   `_verify`(쪽 수·텍스트 재추출)로 다시 검증해 문제 쪽이 줄었을 때만 채택합니다. OCRmyPDF 출력은 쪽 단위로 독립입니다.
3. 임계값 목록은 그대로(1.2 → 0.5). 0.9 를 더하면 시도(=OCR 실행)가 늘고, 병합이 있으면 필요하지 않습니다.

| 코퍼스 글꼴 (macOS) | 수정 전 기본 엔진 3쪽 / 4쪽 | 수정 후 기본 엔진 3쪽 / 4쪽 |
| --- | --- | --- |
| 나눔바른고딕 Regular | 0.89 / 1.00 | 0.89 / 1.00 |
| 나눔바른고딕 Light | 0.87 / 0.97 | 0.87 / 0.97 |
| NotoSansKR Regular | 0.94 / **0.05** (엔진 `rotate-threshold=0.5`, 4쪽 쓰레기가 의심으로 안 잡힘) | 0.94 / 1.00 (3쪽은 0.5, 4쪽은 1.2 시도에서) |
| 나눔스퀘어 R | 0.05 / 0.97 | 0.05 / 0.97 (어느 시도에서도 읽히지 않아 `partial`·의심 표시 유지) |

## 한계

- 비용: 의심 쪽이 있는 문서만 OCR 을 한 번 더 돌립니다(최대 2회, 기존과 같음). 병합은 새 OCR 을 돌리지 않습니다.
- 병합본 PDF 는 pypdf 로 쪽을 다시 쓴 것이라 문서 수준 메타데이터는 OCRmyPDF 출력과 다를 수 있습니다(쪽 내용·텍스트층·`/Rotate` 는 유지).
- 어느 시도에서도 읽을 수 없는 쪽은 복구하지 못하고 `partial`(검토)로 남깁니다.
- 합성 4글꼴·macOS 만 측정했습니다. **Windows(Tesseract 5.4.0)에서의 재측정은 이 PR 에서 하지 않았습니다**
  (시험 머신에 이전 OCR 환경이 남아 있지 않고 Tesseract 추출이 필요해 총괄 확인 대상). 재현 방법:
  `SCANINBOX_TEST_FONTS=<TTF 경로들을 OS 경로 구분자로 연결>` 로 `pytest tests/test_ocr.py -k other_fonts`.
