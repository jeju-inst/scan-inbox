# G0 시험 결과: Windows 네이티브 OCR 파이프라인 (OCRmyPDF + Tesseract)

시험일: 2026-11-05. 시험자: worker2(claude/scan-inbox-worker-2). 형식은 `docs/PILOT.md`의 결과 템플릿을 따릅니다. 상태 표기는 `충족 / 설정 필요 / 확장 필요 / 불가 / 미시험`입니다.

이 문서는 **합성 코퍼스(23건, `main`의 `scaninbox_corpus`)** 로 Windows 11 x64 시험 머신에서 수행한 **사전 시험**입니다. 일반 성능을 보장하지 않습니다. 사용자 파일·실제 스캔 폴더는 열지 않았고 시험은 격리된 새 폴더(`<G0>` 로 표기)에서만 했습니다. 외부 서비스로 문서를 보내지 않았습니다(내려받기만 수행). WSL은 쓰지 않았습니다.

### 환경과 설치 단계·관리자 권한 요구

- 환경: Windows 11 Home x64(빌드 10.0.26300), Core i5-10400(6코어/12스레드), RAM 16GB, 한국어 로캘. 시험은 **비관리자 계정, 원격 셸(SSH)** 로 수행해서 UAC 승인이 불가능한 조건이었습니다. 이 환경에 `LongPathsEnabled=0`, 환경변수 `PYTHONUTF8=1` 이 설정돼 있었고 대소문자 구분은 꺼져 있었습니다.
- **Tesseract: 설치 프로그램을 실행하지 않았습니다.** UB-Mannheim 패키지는 NSIS(nullsoft) 설치 파일이라 일반 설치는 `Program Files` 쓰기·PATH 등록 때문에 관리자 권한이 필요할 가능성이 큽니다(**이 시험에서 실제로 실행해 확인하지는 않음 → 미시험**). 대신 설치 파일을 이미 있던 7-Zip(`7z x`)으로 격리 폴더에 풀어(2.6초, 풀린 크기 약 240MB) `tesseract.exe` 를 직접 실행했습니다. 레지스트리·PATH 변경이 없고 `TESSDATA_PREFIX`·`PATH` 는 자식 프로세스 환경에만 줬습니다.
- **한글 데이터는 설치 파일에 들어 있지 않습니다**(포함 언어 `eng`, `osd` 뿐). `kor.traineddata` 를 GitHub에서 별도로 받아(1.9초) `tessdata` 폴더에 넣어야 `kor+eng` 가 됩니다. 일반 설치 프로그램에서는 언어 선택 항목으로 내려받는 단계입니다. 오프라인 배포를 하려면 이 파일을 함께 묶어야 합니다.
- OCRmyPDF: `uv venv` 로 격리 가상환경을 만들고 `uv pip install` (35패키지, 약 7.7초 — 내려받기 포함). **전부 Windows 휠이라 컴파일러가 필요 없었고** 관리자 권한도 필요 없었습니다. 시스템 Python 의 site-packages 는 건드리지 않았습니다(시험 전후 패키지 수 46개 동일).
- 총 소요(설치 파일 내려받기 18초 + 추출 3초 + 언어 데이터 2초 + venv·패키지 8초): **약 30초.** 사람이 개입한 대기·승인은 없었습니다. 내려받기 용량은 설치 파일 50MB + 휠 수십 MB + 언어 데이터 1.7MB.
- **Ghostscript**: 필요 없음. OCRmyPDF 17 계열은 래스터화에 pypdfium2 를 씁니다(Ghostscript 미설치 상태에서 23건 전부 처리됨, 실패 2건은 의도된 손상·암호화 입력). 다만 **다른 버전(16 이하)에서는 Ghostscript 가 필수**이므로 버전 고정이 필요합니다. PDF/A 출력(기본값)도 Ghostscript 없이 `rc=0` 으로 만들어졌습니다. PDF/A 의 적합성 검증(veraPDF 등)은 하지 않았습니다.
- 선택 의존성 `pngquant`·`unpaper` 는 설치하지 않았습니다. `pngquant` 없음 경고가 한 번 나왔고 처리에는 영향이 없었습니다.
- 이름 정리: 관리자 권한이 필요한 형태의 설치(winget 설치, Program Files, 전역 PATH)는 하지 않았으므로, **"깨끗한 Windows 사용자 환경의 일반 설치·제거" 시험(PILOT 필수 통과 조건)은 미시험**입니다.

### 합성/승인 복사본 여부와 표본 구성

- **합성만 사용.** `python -m scaninbox_corpus.generate --font C:\Windows\Fonts\malgun.ttf --out <G0>\work\corpus_out --force` 로 입력 PDF 23건 생성(8.4초). 구성은 `scaninbox_corpus/README.md` 표와 같습니다(한글 스캔 4, 제목 없는 서식 2, 영문 2, 한영 혼합 2, 텍스트층 2, 혼합 1, 회전·빈 쪽 1, 다중 문서 1, 이름 충돌 7, 손상·암호화 각 1). 대소문자만 다른 쌍은 이 파일시스템 특성상 코퍼스가 **생략**했고 `manifest.skipped` 에 기록됩니다(의도된 동작).
- 폰트: 코퍼스의 폰트 탐색이 Windows 에서 `NanumBarunGothic.ttf` 만 찾아서, 나눔바른고딕이 없는 이 머신에서는 `--font` 로 맑은 고딕을 지정해야 했습니다(아래 확장 항목). 따라서 **이 시험의 문서는 macOS 시험의 문서와 글자 모양이 다릅니다.**
- 한계: 합성 렌더링(150dpi, 약한 노이즈·기울기)이며 tessdata_fast 모델입니다. 실제 스캐너 출력·손글씨·도장 겹침과 다릅니다. 한글 인식률 수치를 일반화할 수 없습니다.

### OCR 시험 방법

각 입력에 `ocrmypdf -l kor+eng --skip-text --rotate-pages --deskew -j 2 <in> <out>` (출력 형식은 기본값 PDF/A). 처리 후 pypdf 로 쪽 수·추출 텍스트를 확인하고, manifest 의 `expected_title` 이 추출 텍스트에 들어 있는지 NFC 정규화 후 문자열 포함으로 확인했습니다(`공백 무시` 포함 확인을 병기).

### Windows 에서 확인한 파일명·경로 동작 (합성 파일만 사용)

모두 격리 폴더 안에서 수행했고 시험 후 삭제했습니다.

- **NFC/NFD**: NTFS 는 정규화를 하지 않고 이름을 그대로 보존합니다. 같은 글자의 NFC·NFD 이름이 **서로 다른 두 파일로 공존**했습니다. NFD 이름만 있을 때 NFC 문자열로 조회하면 `exists=False` 였고 `ocrmypdf` 는 `File not found` 로 실패했습니다. 코퍼스의 `manifest` 키는 NFC 인데 실제 파일 이름(`한글 파일명 정규화 시험.pdf`)은 NFD 로 만들어져 있어서, **manifest 키로 곧바로 파일을 열면 이 건만 실패**했습니다(`rc=2`). 앱·하네스는 이름 비교·조회에 정규화(NFC 로 통일)가 필요하고, 파일 열기는 디렉터리 열거로 얻은 원래 이름을 그대로 써야 합니다. NFD 출력 이름으로 쓰기는 정상이었고 그대로 NFD 로 목록에 나옵니다.
- **대소문자만 다른 이름**: `Report.pdf` 와 `report.PDF` 는 **같은 파일**이라 두 번째 쓰기가 첫 번째를 덮어썼습니다(1바이트로 바뀜). 앱은 이름 충돌 검사를 대소문자 무시로 해야 하고, 덮어쓰기 금지 규칙을 파일 시스템 의존에 맡기면 안 됩니다.
- **예약 이름**: 이 Windows 11 빌드에서는 `CON.pdf`, `COM1.pdf`, `LPT1.pdf`, `aux.txt` 가 일반 경로로 생성되고 OCR 입력으로도 쓸 수 있었습니다. 확장자 없는 `NUL` 은 생성 실패(`WinError 1`)였고 `con` 은 생성 후 목록에 나타났습니다(장치 쓰기인지 실제 파일인지는 확인하지 않음). 이 동작은 Windows 버전별로 다를 수 있어 **다른 버전에서의 재현은 미시험**입니다. 앱은 예약 이름을 이동 목적 이름으로 만들지 않도록 검증해야 합니다.
- **후행 점·공백**: 일반 경로 API 는 `trail.pdf.`·`trail2.pdf ` 의 후행 점·공백을 **조용히 제거**해 다른 이름 파일을 만듭니다. `\\?\` 접두 경로로는 후행 점·공백이 있는 파일이 실제로 만들어지고, 그 파일은 `\\?\` 접두 경로로만 OCR 입력이 되며 일반 경로로는 `File not found` 였습니다. 스캐너·동기화 도구가 이런 이름을 만들면 앱이 열거 결과를 일반 경로로 다시 열 때 실패할 수 있습니다.
- **금지 문자** (`<`, `:` 등): 생성이 실패했습니다. 제안 제목에서 제거·치환해야 합니다.
- **`MAX_PATH`(260자)**: `LongPathsEnabled=0` 환경에서 280자 디렉터리는 일반 `mkdir` 이 실패했고 `\\?\` 접두로만 만들 수 있었습니다. 그 파일은 일반 경로로는 존재 검사가 거짓이고 `ocrmypdf` 입력은 `\\?\` 접두를 붙이면 성공했으며, 출력을 긴 경로로 쓰면 `OutputFileAccessError` 였습니다. **코퍼스의 "긴 한글 경로" 는 228자라 이 한계를 시험하지 못합니다.** 사용자 폴더 아래에 쓰는 한글 긴 경로가 260자를 넘는 현장이 있을 수 있으므로 코퍼스에 260자 초과 케이스(및 생성 옵션)를 추가하는 것을 권고합니다.
- **심볼릭 링크**: 이 비관리자 계정에서 디렉터리 심볼릭 링크 생성이 가능했습니다(개발자 모드 등 계정 설정 영향 가능). 다른 Windows 환경에서는 실패할 수 있어 `junction` 과 함께 별도 시험이 필요합니다.
- 콘솔 출력이 `cp949` 로 디코딩되어 한글이 깨져 보이는 현상은 원격 셸의 출력 처리 때문이었고 파일 처리에는 영향이 없었습니다.

### 코퍼스 하네스의 Windows 동작 (`pytest`)

- 기본 임시 폴더(사용자 `Temp` 아래)에서 `pytest -q`: **3 failed, 5 passed, 9 error.** 실패 원인은 두 가지입니다. ① `MAX_PATH` — 테스트 임시 경로 접두 + 코퍼스의 긴 한글 폴더 3단이 260자를 넘어 `mkdir`/`copytree` 가 실패(2 failed, 9 error). ② 심볼릭 링크 대상 문자열 — `snapshot` 이 기록하는 링크 값이 Python 3.12 Windows 의 `\\?\C:\…` 접두 형태이고 시험은 접두 없는 경로를 기대함(1 failed).
- 짧은 경로로 `--basetemp <G0>\t` 지정: **16 passed, 1 failed** (위 ②만 남음). 코퍼스 생성·결정성·reconcile·snapshot 시험은 통과했습니다.
- 권고: ① 시험 임시 경로를 짧게 하거나 `\\?\` 정규화를 코드·시험에 반영, ② snapshot 의 symlink 대상 문자열에서 `\\?\` 접두를 정규화, ③ `fonts.py` 가 Windows 의 `C:\Windows\Fonts`·사용자 폰트 폴더를 탐색하도록(또는 OFL 폰트 설치 안내), ④ manifest 의 폰트 라이선스 필드가 `--font` 로 다른 폰트를 지정해도 고정 문구(SIL OFL)로 기록될 수 있으므로 지정 폰트의 실제 라이선스를 기록하도록(**이 시험에서는 맑은 고딕을 썼으며 OFL 이 아닙니다. 생성물은 공개 저장소에 올리지 않았습니다**).

### 원본 해시·입력/완료/보류/실패 대조 결과

- 입력 23건 → OCR 성공 21건(`rc=0`), 의도된 실패 2건(손상 `rc=2`, 암호화 `rc=8`), 정답 manifest 의 `expected_outcome=fail` 두 건과 일치. NFD 파일명 1건은 manifest 키(NFC)로 열려다 실패했으나 이는 시험 스크립트의 조회 방식 때문이며 NFD 이름으로 직접 열면 성공했습니다(위 절). 이 시험은 `reconcile` ledger 를 만들지 않아 `완료 + 보류 + 실패 + 미착수 = 입력` 프로그램 검증은 수행하지 않았습니다. 입력 폴더는 `snapshot verify` 로 무변경 확인했습니다(원본은 읽기만 하고 출력은 별도 폴더).

### 전송·민감정보·라이선스 검토 결과

- 전송: 문서·OCR 텍스트를 외부로 보내지 않았습니다. 내려받은 것은 소프트웨어 패키지 3종(Tesseract 설치 파일, `kor.traineddata`, PyPI 휠)이며 패킷 단위 감시는 하지 않았습니다. OCRmyPDF·Tesseract 는 기본적으로 외부 전송이 없는 로컬 실행입니다.
- 민감정보: 합성 문서만 사용했고 실경로·호스트 이름은 기록하지 않았습니다.
- 라이선스: Tesseract Apache-2.0(바이너리에 포함된 라이브러리 라이선스는 재배포 시 별도 확인), `kor.traineddata` Apache-2.0(tessdata 저장소 기준, 재배포 시 확인), OCRmyPDF MPL-2.0. Ghostscript 는 사용하지 않았으므로 AGPL 배포 의무가 발생하지 않았습니다. **다만 시스템 Python 외 인터프리터를 번들하면 해당 배포 의무를 따로 검토해야 합니다.** 법률 검토는 별도입니다.

### 채택/설정 보완/부분 확장/신규 개발 권고와 근거

- 권고: **설정 보완** — OCRmyPDF 17.13.0 + Tesseract 5.4 `kor+eng` 는 Windows 네이티브(WSL 없이)에서 Ghostscript 없이 동작합니다. 설정·확장이 필요한 부분은 다음과 같습니다.
  1. **한글 인식 품질**: 합성 표본에서 제목이 완전히 검색되지 않는 문서가 있어 `tessdata_best`·해상도·전처리 옵션 비교와 실문서 대표 복사본 시험이 필요합니다.
  2. **텍스트 0자 쪽·`/Rotate` 쪽 감지**: OCRmyPDF 의 `rc=0` 만으로 성공 처리하지 않고 쪽별 텍스트 검증을 앱이 수행해야 합니다.
  3. **PDF/A 기본값의 용량 증가**: 출력 형식 옵션 결정.
  4. **Windows 경로·이름 정책**: NFC/NFD 정규화, 대소문자 무시 충돌, 예약 이름·후행 점·공백·금지 문자, `MAX_PATH` 초과(`\\?\` 처리) 를 앱 수준에서 처리해야 하며 이를 코퍼스·시험에 반영해야 합니다.
  5. **Tesseract 배포**: 관리자 권한 없는 사용자 설치·언어 데이터 포함 방식 결정(정식 설치·제거는 미시험).
- 신규 개발 여부는 이번 결과만으로 결정할 수 없습니다(OCR 엔진 자체는 OSS 를 그대로 쓸 수 있다는 점만 확인).
