# G0 재시험 결과: Paperless-ngx × 합성 코퍼스

시험일: 2026-11-05. 시험자: scan-inbox-worker-1(claude/scan-inbox-worker-1). 이전 시험([paperless-results.md](paperless-results.md), 임시 가상 PDF 8건)을 `scaninbox_corpus` 합성 코퍼스(23건, seed 20261105)로 다시 수행한 것입니다. 기준은 `docs/PILOT.md` 필수 통과 조건입니다. 상태 표기는 `충족 / 설정 필요 / 확장 필요 / 불가 / 미시험`입니다.

**한계**: 합성 코퍼스는 단일 글꼴·150dpi·인위 노이즈여서 실스캔 품질을 대표하지 않습니다. 아래 OCR 수치는 이 코퍼스에 한정되며 일반 성능이 아닙니다. 실문서·실경로는 열지 않았고 외부 AI 기능(Paperless AI 등)은 켜지 않았습니다. 외부 통신은 컨테이너 시작 시 `tesseract-ocr-kor` apt 설치뿐이며 패킷 단위 감시는 하지 않았습니다.

## 환경

- Paperless-ngx 3.4.2(이전과 동일 고정), `docker-compose.sqlite.yml` 이미지 태그만 고정, 포트는 `127.0.0.1` 루프백. `PAPERLESS_OCR_LANGUAGE=kor+eng`, `PAPERLESS_CONSUMER_POLLING=5`, `PAPERLESS_CONSUMER_RECURSIVE=true`.
- 컨테이너 내부: OCRmyPDF 17.12.1, Tesseract 5(kor·eng·osd). macOS arm64, Docker Desktop 29.9.2.
- 코퍼스: `python -m scaninbox_corpus.generate --force`로 생성한 입력 23건(하위 폴더 포함). 생성 전 `snapshot create`로 입력 스냅샷을 떠 두었고 Paperless에는 **복사본**만 투입했습니다.

## 1. 한글 OCR 품질: 엔진 탓인가, 이전 렌더링 탓인가

이전의 "큰 제목줄·일부 행 누락"은 **이번 코퍼스에서는 재현되지 않았습니다.** 한글 제목 스캔 4건(문서 요소 15문단·표·제목·직인 등)에서 Paperless 기본 설정의 요소별 문자 재현율은 평균 **99.1%**, 제목 정확 포함 4/4, 본문 문단 90% 이상 재현 15/15였습니다. 따라서 이전 누락은 임시 가상 PDF의 렌더링(저해상도·글꼴 크기 등) 요인이 컸다고 판단합니다. 다만 실스캔에서의 일반화는 별도 시험(PILOT 3단계)이 필요합니다.

컨테이너 안에서 OCRmyPDF+Tesseract `kor+eng`를 Paperless 없이 단독으로 같은 코퍼스에 돌려 비교했습니다(한글 4건 기준, 요소별 문자 재현율 평균 / 제목 정확 포함).

| 변형 | 옵션 | 재현율 | 제목 |
| --- | --- | --- | --- |
| A | 기본(`--skip-text`) | 97.1% | 4/4 |
| B | + 회전 임계값 2 | 97.1% | 4/4 |
| C | + `--deskew` | **99.0%** | 4/4 |
| D | C + `--oversample 300` | 96.7% | 3/4 |
| E | C + `--tesseract-pagesegmode 6` | 75.8% | 3/4 |

- Paperless 기본 설정(deskew 사용)의 99.1%는 변형 C와 같은 수준이라 **Paperless가 엔진 품질을 깎지 않습니다.** 엔진 결과는 OCRmyPDF 단독과 사실상 동일합니다.
- 해상도 올리기(D)와 페이지 분할 모드 고정(E)은 이 코퍼스에서 개선이 아니라 악화였습니다. 특히 E는 빈 페이지 노이즈에서 쓰레기 텍스트를 만들었습니다. 임의 옵션 튜닝보다 기본 + deskew가 낫습니다.
- 영문·한영 혼합 제목은 전 변형에서 정확 포함(100%)이었습니다. 텍스트층 PDF·혼합 PDF의 텍스트층 쪽은 `--skip-text`로 보존되었고 스캔 쪽만 OCR되었습니다(쪽 수 보존).
- 한계: 한글 폰트 대체 경고(`No installed font has glyphs for 'kor' text`)가 PDF/A 생성 중 나옵니다. 텍스트층은 보이지 않는 글꼴로 추가되어 검색에는 문제없었지만 PDF/A 폰트 임베딩 상태는 확인하지 않았습니다.

## 2. 90도 회전 페이지와 임계값 조정

대상은 `rotated_blank` 파일(1쪽 정상, 2쪽 빈 쪽, 3쪽 이미지 90도 회전, 4쪽 PDF `/Rotate 90`, 5쪽 빈 쪽)입니다.

| 임계값 | 3쪽(이미지 회전) | 2쪽(빈 쪽) 회전 여부 | 비고 |
| --- | --- | --- | --- |
| 12(Paperless 기본) | **교정 안 됨**, 본문이 쓰레기 문자 | 안 함 | 방향 신뢰도 1.43 < 12 |
| 2 | 교정 안 됨 | 안 함 | 1.43 < 2 |
| 1.4 / 1.0 | **교정됨**, 본문 정상 인식 | 안 함 | 3쪽 신뢰도 1.43 ≥ 임계값 |
| 0.5 | 교정됨 | **빈 쪽까지 회전** | 빈 쪽 신뢰도 0.83 |
| 0 | 교정됨 | 빈 쪽 회전 + 5쪽도 회전 | 빈 쪽을 모두 돌림 |

- 이 코퍼스에서는 임계값 **1.0〜1.4**가 3쪽만 교정하고 빈 쪽은 건드리지 않았습니다. Paperless에서 `PAPERLESS_OCR_ROTATE_PAGES_THRESHOLD=1.0`으로 컨테이너를 다시 띄워 같은 파일을 투입했을 때도 3쪽 본문이 정상 인식되었고 쪽 수 5가 보존되었습니다. 기본값 12는 이 코퍼스의 회전 쪽을 교정하지 못합니다.
- 단 신뢰도 1.43은 표본 한 쪽의 값입니다. 임계값 1.0이 실스캔에서 오회전을 일으키지 않는다는 근거는 없고, 빈 쪽 신뢰도 0.83과의 마진도 작습니다. **일반 권고값이 아니라 이 코퍼스에서의 관찰값입니다.**
- **4쪽(PDF `/Rotate 90`)은 평가하지 못했습니다.** 입력 PDF를 직접 렌더링하면 4쪽 이미지에 내용이 보이지 않습니다(쪽 크기가 842×595 가로인데 이미지는 세로로 그려져 잘리는 것으로 보임). 어떤 임계값에서도 4쪽 텍스트가 비어 있었습니다. 엔진 한계가 아니라 **코퍼스 생성기(`generate.py`의 pdf_rotate 쪽 처리) 쪽 결함 가능성**이 높아 총괄에 확인을 요청합니다.
- OCR 신뢰도가 낮은 쪽을 자동 성공으로 처리하는 문제는 그대로입니다. 기본 임계값에서 회전 쪽이 쓰레기 문자로 인식되어도 소비는 성공으로 기록되고 검토 상태가 없습니다.

## 3. 중복·이름 충돌 처리

| 상황 | 결과 |
| --- | --- |
| 바이트 동일 파일 재투입 | 경고 로그(`Consuming duplicate … share the same content`)만 남기고 **별도 문서로 등록**(문서 수 22→23). 중복 거부·검토 보류 없음. 이전 결과와 동일 |
| 제안 제목·날짜가 같은 2건(`name_collision`) | 서로 다른 문서 ID로 둘 다 보존, 덮어쓰기 없음. 내보내기 파일명은 ID(`0000NNN.pdf`) 기반이라 충돌하지 않음 |
| 하위 폴더별 같은 파일명(`scan.pdf`) 3건 | 3건 모두 별개 문서로 보존. 단 **원래 폴더 정보는 유지되지 않고** 원본 파일명이 모두 `scan.pdf`가 됨 |
| NFD 한글 파일명 | 정상 소비. 문서 원본 파일명은 NFC/NFD 표기가 섞여 보여 비교 시 정규화 필요 |
| 긴 한글 경로 | 정상 소비 |
| 대소문자 충돌 | 이 파일시스템에서는 생성 불가(manifest `skipped`). 미시험 |
| 소비 후 consume 폴더 | 완료된 파일은 삭제되고 **빈 하위 폴더는 남음** |

덮어쓰기·소실은 없었습니다(충돌 회피는 "충족"). 다만 이는 모든 문서를 ID로 구분하기 때문이며, 사람이 읽는 파일명 충돌 규칙(`YYYY-MM-DD_제목__짧은ID.pdf` 등)은 Paperless에 없습니다.

## 4. reconcile·snapshot 검증

- **입력 무변경(`snapshot verify`)**: Paperless에는 복사본만 투입했으므로 원본 코퍼스 입력은 `파일 23건 이름·크기·해시·mtime 동일`로 통과했습니다. 반대로 Paperless의 consume 폴더(실제 입력 역할)에 대해 verify를 돌리면 소비된 파일이 모두 `removed`로 보고됩니다. 하네스가 "소비는 입력을 삭제한다"를 정확히 검출함을 확인한 것이며, Paperless는 처리 전 미리보기 단계(무변경 preview)가 없어 이 조건을 해당 방식으로는 충족하지 않습니다.
- **건수 대조(`reconcile`)**: Paperless 작업 결과와 내보낸 원본의 SHA-256로 ledger를 만들어 돌렸습니다(완료 22 + 보류 0 + 실패 1 + 미착수 0 = 입력 23). 하네스가 보고한 위반 2건:
  1. `encrypted_pdf`(열기 암호 PDF)가 **성공으로 소비되어 완료로 기록됨**(페이지 수 없음·본문 0자의 빈 문서가 등록됨). 하네스의 `[실패 위장]` 검출과 일치합니다. 이것이 이번 시험의 가장 중요한 필수 조건 위반입니다.
  2. 완료 폴더에 미리 있던 파일 소실 보고는 **시험 구성의 산물**입니다. Paperless에는 "완료 폴더" 개념이 없어 사전 파일을 둘 곳이 없었으므로 Paperless의 덮어쓰기가 아닙니다. 이 항목은 평가 대상에서 제외합니다.
- 손상 PDF(`corrupt_pdf`)는 정상적으로 실패 처리되어 consume에 남았고 `failed`로 기록되었습니다(위 대조에서 위반 아님).
- 하네스가 검사하지 않는 항목: 기대 결과가 `review`(제목 없는 서식 2건, 다중 문서 묶음 1건)인 파일이 Paperless에서 모두 **그냥 완료로 등록**된 점은 위반으로 보고되지 않았습니다. 수동으로 확인한 결과이며, reconcile 하네스에 "기대 review인데 completed" 검사를 추가할 필요가 있습니다.

## 5. 그 밖에 이번에 확정된 사항

- **문서 날짜**: 본문의 날짜가 있는데도 한글 표기(`2026. 3. 12.`)는 Paperless 날짜 파서가 인식하지 못해 생성일이 **투입일(2026-11-05)** 로 들어간 건이 많았습니다(날짜가 있는 14건 중 일치 3건, 영문 표기만 일치). `PAPERLESS_DATE_ORDER=YMD`로 바꿔도 같은 입력에서 개선되지 않았습니다(8건 재투입 중 영문 1건만 일치). 날짜가 없는 문서(제목 없는 서식 2건)는 투입일이 들어갔고 다중 문서 묶음은 묶음 속 한 문서의 날짜(2026-04-24)가 전체 날짜로 들어갔습니다. 즉 "날짜를 조작하지 않음" 조건은 충족하지 못하며 투입일 폴백이 사용자에게 보이지 않습니다.
- **제목**: 기본은 파일명입니다(이전 결과와 동일). 본문 기반 제목은 없습니다.
- **다중 문서 묶음**: 5쪽 한 문서로 등록, 분리·검토 표시 없음.
- 필수 통과 조건 중 이번에도 시험하지 못한 것: 재시작·강제 종료·장애 주입, 디스크 부족·권한 거절·잠긴 파일, Windows 환경, 사용자 승인 후 배치·Undo.

## 결론

| 이전 미결 항목 | 이번 확정 |
| --- | --- |
| 한글 OCR 누락이 렌더링 탓인지 엔진 탓인지 | 합성 코퍼스에서는 99% 재현. 이전 누락은 **임시 PDF 렌더링 요인**이 컸음. Paperless는 OCRmyPDF 단독과 동일 품질 |
| 회전 교정과 임계값 | 기본값(12)은 회전 쪽을 교정하지 못함. 1.0〜1.4에서 교정(빈 쪽 오회전 없음). 값은 코퍼스 한정 관찰 |
| 중복·이름 충돌 | 덮어쓰기·소실 없음, 단 중복 통합·거부 없음, 폴더 정보 소실 |
| 입력 무변경·대조 검증 | 하네스로 자동 검증 가능. **암호화 PDF 성공 위장**과 날짜 투입일 폴백이 새로 확인된 위반 |

권고는 이전과 같이 **부분 확장(조건부)** 입니다. 이번 시험으로 OCR 품질은 Paperless 채택의 걸림돌이 아님이 확인되었으나, 암호화·OCR 품질 미달의 성공 위장, 날짜 처리, 승인 후 배치·Undo 부재는 후처리 확장 없이는 해결되지 않습니다.

## 정리 내역

- `docker compose down -v --rmi all`로 컨테이너·볼륨·네트워크·이미지를 모두 삭제했고 `docker ps -a`·`docker volume ls`·`docker images`가 비었음을 확인했습니다.
- 격리 임시 디렉터리(compose·env·소비/내보내기 폴더·생성 코퍼스·OCR 출력)는 시험 후 삭제했습니다. 비밀번호·키는 기록하지 않았습니다.
- 시험을 위해 Docker Desktop을 실행했습니다(시험 전 꺼져 있었음).
