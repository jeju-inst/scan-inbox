작성일: 2026-11-05. 근거는 `docs/g0/` 아래 시험 문서와 PR #1〜#7입니다. 모든 시험은 완전 가상 합성 자료와 격리 환경에서 했고 실문서는 열지 않았습니다. 아래 권고는 제안이며 채택 방향은 사용자가 결정합니다.

## 2. 기존 OSS가 못 채우는 경계

PILOT 필수 조건 중 어느 후보도 단독으로 채우지 못하는 것은 같습니다.

1. 승인 후 배치(미리보기 → 승인 → 최종 배치)와 입력↔최종본 ledger
2. 검토 대상(제목 없음·다중 문서·OCR 불량·암호화)을 자동 완료하지 않는 상태 관리
3. 원본 별도 보존과 Undo
4. 크래시 복구(journal)와 충돌 없는 덮어쓰기 금지 배치

Paperless는 1·3을 일부 대체하는 보관소 모델이라 "스캔 폴더를 미처리함으로 유지하고 업무 폴더로 정리"하는 요구와 맞지 않습니다. organize는 2·3·4가 없습니다.

## 3. 시험으로 새로 드러난 함정 (설계에 반영)

- **OCR**: kor 언어팩은 두 OS 모두 기본 미포함이라 설치 단계에서 받아야 함. 옵션에 따라 인식이 흔들림(`--oversample 300`·`psm 6`은 악화, 기본+deskew가 최선). tessdata_fast·150dpi·합성 글꼴 기준이라 **실문서 표본으로 재측정 필요**.
- **PDF `/Rotate 90`**: 기본 설정에서 OCR 텍스트 0자인데 종료코드 0. 회전 임계값 1.0〜1.4에서 교정(코퍼스 한정). 앱이 **쪽별 텍스트 검증**을 해야 함.
- **성공 위장**: 도구가 성공으로 보고해도 암호화·무텍스트·회전 쪽이 있음. 완료 판정은 앱 검증으로.
- **Windows 파일명**: NTFS는 NFC/NFD를 별개 파일로 공존시키고, 대소문자만 다른 이름은 동일 파일(덮어쓰기), 후행 점·공백 제거, 260자 초과는 `\\?\` 필요(LongPathsEnabled=0). PLAN §5의 충돌 검사가 필수.
- **PDF/A 출력**: macOS 용량 약 20% 감소, Windows 약 3.7배 증가. 출력 형식·크기 정책 필요.
- **한글 날짜 표기**: Paperless 파서가 읽지 못해 투입일로 폴백. 날짜는 앱이 직접 추출하고 불명은 불명으로 표기.

## 4. 권고

**신규 개발(G1 진행)을 권고합니다.** 범위는 좁게 잡습니다.

- 핵심은 에이전트 중립 Python CLI. 보호(원본 보존) → 추출(OCRmyPDF) → 제안 → 승인 → 배치 → 복구 수직 절편, SQLite journal, 기존 코퍼스 하네스로 인수 검증.
- OCR·PDF 처리는 검증된 부품(OCRmyPDF/Tesseract)을 하위 프로세스로 사용. 새로 만들지 않음.
- 제목 제안은 규칙(OCR 첫 제목줄·문서번호·날짜 패턴)으로 시작하고 **LLM은 G1 범위에서 제외**. 구독 CLI는 OS 격리 설계가 서야 도입(PLAN §6.1 유지). 격리 못 하는 어댑터는 자동 분석 금지.
- UI(트레이·검토 화면)는 G2. G1은 CLI와 미리보기 출력으로 끝냄.

대안(Paperless 채택)은 **"스캔 폴더 유지·업무 폴더 이동"을 포기하고 보관소·웹 UI·서버 운영을 받아들일 때만** 성립합니다. 이 경우에도 승인 후 배치·Undo·검토 큐 없이 운영하게 됩니다.

## 4.1 구독 CLI 어댑터가 지켜야 할 요건 (Windows 시험에서 도출)

- 문서 내용은 **stdin으로만** 전달하고 명령줄 인자에 넣지 않음. 인자에 `%VAR%`가 있으면 cmd.exe가 치환해 환경값이 프롬프트로 새어 나감(npm shim 경유 시).
- 가능하면 shim(`*.cmd`)이 아니라 **네이티브 실행 파일을 직접 실행**. 인자는 배열로 전달하고 셸을 거치지 않음.
- 취소·시간 초과 시 **프로세스 트리 전체를 종료**(Windows `taskkill /T /F` 등). 부모만 종료하면 자식이 고아로 남음.
- 인증 상태는 CLI의 상태 명령(토큰 미출력)으로 판별하고, 로그아웃·한도 소진은 보류로 처리(다른 공급자로 우회 금지).
- 도구·MCP를 끄는 플래그는 필수이나 격리 보장으로 간주하지 않음. 플래그 효과는 CLI·버전·OS별로 재시험(Codex `-s read-only`는 macOS와 Windows 결과가 달라 원인 미확인).
- CLI 버전이 OS·시점마다 달라 결과가 달라지므로 어댑터는 시작 시 버전을 기록하고 검증된 버전 범위만 자동 분석에 허용.

## 5. 아직 모르는 것

- 실문서 한글 OCR 품질(폰트·해상도·도장·표). 승인된 복사본 시험 필요(G3 선행).
- AI File Sorter 적합성. 시험하려면 Homebrew 전역 변경 또는 격리 빌드, 모델 다운로드, GUI 조작에 대한 사용자 승인이 필요. 위 결론을 뒤집을 가능성은 낮다고 보지만 미확인.
- 구독 CLI 약관상 앱의 하위 프로세스 호출 허용 여부(공식 문서 확인 필요), Windows 동작(worker 시험 진행 중).
- 설치 패키징·서명·공증, 정식 Windows 설치·제거 시험.

## 6. 사용자 결정이 필요한 것

1. 위 권고(신규 개발 G1)를 승인할지, Paperless 채택으로 갈지.
2. PLAN §8의 완료함 의미(최종본 보관처 / 원본 아카이브 / 완료 목록), OCR 필수 여부. G1 설계 전에 정해야 함.
3. AI File Sorter 시험을 진행할지(위 승인 항목).
4. 실문서 복사본 시험 범위(G3 선행)와 시점.
