# G0 시험 결과: Paperless-ngx

시험일: 2026-11-05. 시험자: worker2(claude/scan-inbox-worker2). 형식은 `docs/PILOT.md`의 필수 통과 조건·결과 템플릿을 따릅니다. 상태 표기는 `충족 / 설정 필요 / 확장 필요 / 불가 / 미시험`입니다.

이 문서는 **합성 소표본(PDF 8건)** 시험이며 일반 성능을 보장하지 않습니다. 실제 스캔 폴더·실문서는 열지 않았고, 모든 입력은 완전 가상 내용입니다. 외부 AI·원격 서비스로 문서를 보내지 않았고 Paperless AI 기능은 켜지 않았습니다.

## 결과 템플릿

### 대상 OSS/앱과 고정 버전

- Paperless-ngx **3.4.2**(2026-11-03 배포 정식 릴리스, GitHub API `prerelease=false` 확인). 이미지 `ghcr.io/paperless-ngx/paperless-ngx:3.4.2`, 공식 `docker-compose.sqlite.yml`(해당 태그 소스)을 받아 이미지 태그만 `latest`에서 `3.4.2`로 고정했습니다. 브로커는 `valkey/valkey:9-alpine`.
- 컨테이너 내부 확인값: Tesseract 5, Ghostscript 10.05.1(OCRmyPDF가 PDF/A 변환 시 "10.7.0 이상 권장" 경고를 냄), 언어 `kor`·`eng`·`osd` 설치.
- 라이선스: GPL-3.0(저장소 메타데이터 기준).

### 환경과 설치 단계·관리자 권한 요구

- 환경: macOS(Darwin 25.6, Apple Silicon arm64, 64GB), Docker Desktop 29.9.2(VM 메모리 한도 약 7.7GiB). 로컬 포트는 `127.0.0.1:18010`로 루프백에만 공개했습니다.
- 단계: compose 파일·env 파일 준비 → `docker compose pull/up` → 자동으로 관리자 계정 생성 → 폴더 감시 시작. 이미지 크기 약 2.4GB, 기동 후 webserver 약 1.0GiB·broker 약 29MiB 메모리. 설치 자체는 Docker가 이미 있으면 수 분입니다.
- 관리자 권한: Docker Desktop이 이미 설치·로그인되어 있었으므로 이 시험에서 별도 sudo는 요구되지 않았습니다. Docker Desktop 설치 자체의 권한 요구와 **기관 규모에 따른 Docker Desktop 상용 라이선스 조건은 이번에 확인하지 못했으며, 채택 시 별도 확인이 필요합니다.**
- 한글 OCR 언어팩 `PAPERLESS_OCR_LANGUAGES=kor`는 **컨테이너가 시작될 때마다 apt로 내려받아 설치**합니다(로그 `init-tesseract-langs`). 컨테이너를 새로 만들 때 네트워크가 필요합니다. 폐쇄망이면 언어팩을 포함한 커스텀 이미지가 필요합니다.
- `PAPERLESS_OCR_LANGUAGE=kor+eng`는 설정되었고 실제 OCR에 적용되었습니다(한글·영문이 함께 인식됨).

### 합성/승인 복사본 여부와 표본 구성

- 합성만 사용. 승인된 실문서 복사본은 사용하지 않았습니다. worker1의 `feat/corpus` PR은 시험 시점에 올라와 있지 않아(`gh pr list`에 PR #1만 존재) 직접 만든 가상 PDF를 사용했습니다. 코퍼스가 올라오면 같은 절차로 재시험해야 합니다.
- 표본(모두 이미지 전용, 텍스트층 없음): ① 한글 제목이 있는 문서(저해상도 약 200dpi), ② 제목 없는 한글 서식, ③ 영문·한영 혼합, ④ 다중 페이지(2쪽째 90도 회전), ⑤ ①의 바이트 동일 사본(중복), ⑥ 300dpi A4에 잡티·기울기를 준 한글 공문 유사 문서, ⑦ ⑥을 90도 회전한 문서, ⑧ ⑥의 사본(규칙 시험용). 이후 영문 문서 사본 1건(워크플로 시험)과 손상 파일 1건(임의 바이트를 `.pdf`로 저장)을 추가했습니다.
- **한계**: 이미지는 합성 렌더링이어서 실제 스캐너 출력의 노이즈·서식·글꼴과 다릅니다. 한글 OCR 정확도 수치를 일반화할 수 없습니다. 이 표본에는 암호화·서명 PDF, 다중 문서 묶음, 빈 페이지, 디스크 부족, 강제 종료 등은 포함하지 않았습니다.

### 제목·OCR·분류·완료함·복구별 충족/미충족/미시험

| 항목 | 상태 | 관찰 |
| --- | --- | --- |
| 입력 폴더 비움(완료 건만) | 충족 | 소비에 성공한 파일은 consume에서 삭제됨. 손상 파일은 consume에 남고 `Unsupported mime type` 사유가 로그와 tasks에 표시됨. 단 이 동작은 "처리 완료 폴더로 이동"이 아니라 "삭제"임 |
| 원본 보존 | 충족 | 처음 투입한 5건의 보관소 원본이 입력과 SHA-256 일치. 원본과 별개로 OCR 적용 archive PDF(PDF/A-2b)를 따로 생성(원본 약 70〜140KB → archive 약 17〜40KB) |
| 원본 해시 일치 | 충족 | 내보낸 원본도 입력 해시와 일치(5/5) |
| 한글 OCR(`kor+eng`) | 설정 필요 | 영문·혼합은 양호. 한글은 **큰 제목줄과 일부 행을 통째로 누락**했고 정확한 문장 사이에 잡음 문자가 섞임. 예: 한글 제목 문서에서 제목줄 누락, 공문 유사 문서에서 첫 3줄과 "협조하여" 줄 누락. 합성 렌더링 탓일 수 있어 결론을 내릴 수 없음. 실제 스캔 표본으로 재시험 필요 |
| 회전 페이지 교정 | 설정 필요 | 90도 회전 입력은 자동 교정되지 않았고 본문이 사실상 읽히지 않음(로그에 방향 신뢰도 낮음 메시지). 임계값·옵션 조정은 시험하지 않음 |
| OCR 실패의 자동 성공화 금지 | 미충족(확장 필요) | 읽을 수 없는 쓰레기 텍스트가 나와도 소비는 **성공**으로 기록되고 검토 상태가 없음. 신뢰도 기반 검토 보류를 하려면 후처리 확장 필요 |
| 페이지 수 보존 | 충족 | 1쪽·2쪽 문서 모두 `page_count` 일치 |
| 제목: 문서 본문에서 추출 | 확장 필요 | 기본 제목은 **파일명**. 본문 기반 제목 추출은 기본 기능에 없음(AI 제안 기능은 있으나 외부 AI 사용 금지로 끔) |
| 제목: 템플릿 | 설정 필요 | 워크플로 `assign_title`은 소비 시점에 사용 가능한 변수가 제한적임. `{{ created }}`는 `'created' is undefined`로 실패 후 원래 제목으로 **조용히 폴백**(로그에만 ERROR). 파일명 기반 템플릿 외의 이름 규칙은 불가능에 가까움 |
| 분류: 규칙(내용 키워드) | 설정 필요 | 문서유형·storage path에 키워드 일치 규칙이 있음. 워크플로 매칭으로 문서유형·storage path가 지정되어 파일이 `업무/협조요청/2026/` 아래 한글 경로로 저장됨(수동 규칙 지정). 내용 키워드 자동 일치는 OCR에 해당 단어가 있어야 하는데 이번 표본에서는 단어가 OCR에서 누락되어 **시험하지 못함**(워크플로 지정으로만 확인) |
| 중복 처리 | 설정 필요 | 바이트 동일 파일도 경고 로그만 남기고 **별도 문서로 등록**됨. 중복 거부·검토 보류는 기본이 아님 |
| 업무 폴더로 내보내기 | 확장 필요 | 아래 별도 절 |
| Undo(입력 복구) | 불가 | 입력은 삭제되므로 되돌리기에 해당하는 기능 없음. 원본은 보관소(`originals`)에 있어 수동 복원 가능하나 원래 입력 경로로 자동 복구하지 않음 |
| 충돌 회피 | 미시험 | 동일 제목·경로 충돌 시 동작 미확인(동일 제목이 필요한 케이스를 만들지 않음) |
| 재시작·강제 종료·장애 주입 | 미시험 | 시험하지 않음 |
| Windows 환경 | 미시험 | 이 시험은 macOS에서만 수행 |

### 업무 폴더로 내보내는 데 드는 추가 작업

- 기본 구조는 문서 DB와 `media` 보관소가 내부 관리 파일을 소유하는 방식입니다. 일반 업무 폴더를 파일 단위로 직접 관리하지 않습니다.
- **`document_exporter`**(컨테이너 안 명령): 일괄로 폴더에 내보냅니다. `--use-filename-format`을 쓰면 storage path 템플릿대로 하위 폴더(`업무/협조요청/2026/…`)가 만들어지고 원본 바이트가 유지됩니다(해시 5/5 일치). 기본 이름은 `YYYY-MM-DD 제목.pdf`, archive는 `-archive` 접미. `--no-archive`·`--no-thumbnail`로 줄일 수 있습니다.
- 한계: ① **자동이 아닙니다.** 명령 실행(또는 외부 스케줄)이 필요합니다. ② 같은 폴더에 `manifest.json`·`metadata.json`이 함께 생성되어 업무 폴더에 섞입니다. ③ 내보내기는 일방향 복사로, 내보낸 파일을 사람이 옮기거나 고쳐도 Paperless와 동기화되지 않습니다. ④ 한 문서를 "관련 폴더"와 "처리완료" 두 곳에 두려면 별도 스크립트가 필요합니다. 즉 `docs/PLAN.md`의 "최종 위치와 원본 보존 분리"·승인 후 배치 흐름은 **후처리 스크립트 개발이 필요**합니다.
- 사용자 승인 후 이동이라는 개념(검토 큐)이 Paperless에는 없습니다. 있는 것은 인박스 태그 방식의 사후 정리입니다.

### 원본 해시·입력/완료/보류/실패 대조 결과

- 입력 등록 건수 10건: 소비 성공 9건, 실패 1건(손상 파일, 입력에 잔류), 보류 개념 없음, 미착수 0건(9 + 0 + 1 + 0 = 10, 수작업 계산). 성공 9건 중 처음 투입한 5건(①〜⑤)의 보관소 원본 해시와 내보낸 원본 해시가 입력과 일치함을 확인했고, 나머지 4건은 해시 대조를 하지 않았습니다. `완료 + 보류 + 실패 + 미착수 = 입력` 프로그램 검증은 수행하지 않았습니다.
- consume 폴더는 시험 종료 시점에 손상 파일 1건만 남았습니다.

### 전송·민감정보·라이선스 검토 결과

- 전송: 컨테이너 환경에 AI·LLM 관련 설정을 넣지 않았고 AI 제안 기능은 호출되지 않았습니다. 워크플로 모델에는 `ai_suggestion_fields` 항목이 존재하므로 "기본 꺼짐 여부는 설정으로 고정하고 점검"이 필요합니다. 네트워크 송수신을 패킷 단위로 감시하지는 않았습니다. **관찰한 외부 통신**: 컨테이너 시작 시 apt로 `tesseract-ocr-kor` 패키지를 내려받음(문서 내용 전송 아님).
- 민감정보: Paperless는 OCR 본문 전체를 DB·인덱스에 저장하며(검색용), 내부 문서를 서비스 DB에 중복 보유합니다. 접근 제어(계정·권한)와 백업 정책이 필요합니다.
- 라이선스(GPL-3.0): **채택 시 별도 서비스로 운영**하고 MIT 앱에 코드를 복사·링크하지 않으면, 서비스를 HTTP·파일로만 연동하는 한 이 프로젝트 코드에 GPL이 전염되는 구성은 아닙니다. 소스를 수정해 배포하면 GPL 의무가 생깁니다. 법률 검토는 별도입니다.

### 채택/설정 보완/부분 확장/신규 개발 권고와 근거

- 권고: **부분 확장(조건부)** 입니다. 현재 요구 중 입력 비움·원본 보존·OCR·검색 보관소는 충족하거나 설정으로 가능합니다. 반면 다음은 Paperless 기본 기능으로 해결되지 않습니다.
  1. 기존 업무 폴더 구조로의 **승인 후 배치**와 "처리완료 + 관련 폴더" 이중 배치.
  2. 본문 기반 제목 추출과 `YYYY-MM-DD_제목__짧은ID.pdf` 이름 규칙.
  3. Undo, 검토 큐, OCR 품질 미달의 검토 보류.
  4. 중복을 자동 통합하지 않고 사용자에게 제시.
- 위 4가지가 "웹 UI에서 보관소를 쓰는 방식"을 사용자가 받아들일 수 있을 때만 의미가 있고, 폴더 중심 UX를 유지해야 한다면 Paperless는 내부 보관소 모델과 충돌하므로 다른 경로(AI File Sorter, organize+OCR, 경량 자체 앱)와 비교해야 합니다. 이번 결과만으로 "신규 개발 착수"를 결정할 수는 없습니다.
- **한글 OCR 품질은 이번 표본으로 판단 불가.** 엔진은 Tesseract/OCRmyPDF이므로, 이 부분은 Paperless 고유 이점이 아니라 OCRmyPDF 엔진 시험(G0의 별도 항목)과 같은 평가 대상입니다. 어느 경로든 같은 엔진을 쓰면 결과가 동일하게 영향받습니다.
- Windows/macOS 사용성: 네이티브 앱이 아닙니다. 서버 구성요소(Docker, 컨테이너 2개, 포트)를 PC마다 쓰는 구조가 아니라 **공유 서버 1대와 브라우저 접속**이 자연스럽습니다. 이는 `docs/PLAN.md`가 첫 버전 범위에서 제외한 "공유 서버·기관 전체 문서관리시스템" 쪽입니다. 단일 사용자 PC 설치는 Docker Desktop 의존(상시 약 1GiB 이상 메모리, 이미지 2.4GB)이 부담입니다. Docker Desktop for Mac의 바인드 마운트는 파일 이벤트 전달이 불안정할 수 있어 이번에는 `PAPERLESS_CONSUMER_POLLING=5`(5초 폴링)를 썼고 정상 동작했습니다. 로그인 없이 상시 가동하려면 Docker Desktop 자동 시작 설정이 별도로 필요합니다. 스캐너가 쓰는 네트워크 공유 폴더를 consume 마운트로 쓰는 구성은 이번에 시험하지 않았습니다.

### 사용자 승인 및 다음 단계

- 승인 필요 사항: ① Paperless를 "공유 서버 + 웹 UI 보관소" 모델로 계속 평가할지, ② 폴더 중심 UX를 요구사항으로 확정할지.

## 시험 후 정리 내역

- `docker compose down -v --rmi all`로 컨테이너 2개(webserver, broker), 볼륨 3개(data, media, redisdata), 네트워크 1개, 이미지 2개(paperless-ngx 3.4.2, valkey 9-alpine)를 삭제했습니다. 이후 `docker ps -a`·`docker volume ls`·`docker images`가 모두 비어 있음을 확인했습니다.
- 저장소 밖 임시 격리 디렉터리(compose 파일, 임의 생성 비밀키·관리자 비밀번호가 든 env 파일, 가상 입력 PDF, 내보내기 폴더)를 삭제했습니다. 비밀번호·키는 이 저장소에 기록하지 않았습니다.
- 시험을 위해 Docker Desktop을 새로 실행했습니다(시험 전 꺼져 있었음).
