# 제품·안전 설계 초안

작성일: 2026-11-04. 제품명 Scan Inbox는 작업용 명칭입니다. 아래 기술 선택·일정은 제안이며 구현 사실이 아닙니다.

## 1. 범위와 우선순위

- P0: 내용 기반 제목·이름 제안, 수동 일괄 실행, 성공한 문서의 처리완료 이동, 원본 보존·실행 기록·되돌리기.
- P1: 로컬 OCR, 예약 실행·폴더 감시, 기존 적재분 처리, 선택한 관련 폴더 후보 추천.
- P2: 검증된 규칙에 한한 자동 승인·자동 이동, 사용자 피드백을 반영한 분류 개선, 이미지 입력 확장.
- 최초 입력은 PDF. JPEG/PNG/TIFF는 후속 범위이며 복수 스캔의 자동 병합·분할은 제외합니다.
- Windows x64와 macOS Apple Silicon을 첫 검증 대상으로 삼습니다. 다른 CPU 지원은 별도 검증 전까지 주장하지 않습니다.
- 회사 네트워크 스캐너 연결 자체는 기존 기능을 사용합니다. 공유 서버·기관 전체 문서관리시스템은 첫 버전 범위가 아닙니다.

## 2. 최초 설정과 화면

- 스캔 폴더, 처리완료 폴더(제안 기본값: 스캔 폴더의 형제 `scan_처리완료`), 원본 보관 위치, 선택적 관련 문서 루트를 선택합니다.
- 처리완료·원본·관련 타겟을 감시 입력으로 재귀 포함하지 않도록 검사합니다. 타겟을 스캔 폴더 내부로 지정하는 설정은 거절합니다.
- OCR 언어 기본 제안은 `kor+eng`. 엔진·언어팩 가용성, 저장 공간, 읽기·쓰기 권한을 설정 진단에서 확인합니다.
- 트레이 메뉴: 지금 처리, 일시중지, 검토함 열기, 기록·되돌리기, 설정. 앱 종료·로그아웃 시 감시가 멈추는지 명시합니다.
- 검토 목록: 원래 이름, 썸네일, 제목 근거(페이지·짧은 발췌), 새 이름, OCR 상태, 이동 후보·이유, 오류. 항목별 수정·승인·보류 및 일괄 승인을 제공합니다.
- 백그라운드 예약은 앱 실행 중 주기 확인부터 시작합니다. 로그인 자동 시작 및 앱이 닫힌 상태의 실행은 OS별 지원을 검증한 후 제공합니다.

## 3. (3) 관련 폴더와 (4) 처리완료의 관계

한 파일을 두 곳으로 동시에 이동할 수 없으므로 **최종 위치와 원본 보존을 분리**합니다.

- 기본 모드: 이름·OCR가 적용된 최종본을 `scan_처리완료`에 둡니다.
- 선택 모드: 승인된 관련 폴더에 최종본을 둡니다. 처리완료 화면에는 최종 경로와 처리 내역이 남습니다. 스캔 폴더 인근의 완료 이력에서 찾을 수 있도록 로컬 기록을 제공합니다.
- 두 폴더 모두에 최종본이 필요하면 `관련 폴더로 복사 + 처리완료에 보관`을 명시적으로 선택합니다. 두 사본이 독립적이라는 점과 이후 수정 동기화가 없음을 표시합니다. Windows 바로가기와 macOS 별칭에 의존하지 않습니다.
- 모든 모드에서 별도의 원본 보관소에 바이트가 동일한 입력을 먼저 보존합니다. 보관 기한은 기본 무기한이며 삭제·정리는 사용자 명시 동의 후에만 합니다.
- 완료의 의미는 설정 프로파일별입니다. OCR 필수 프로파일은 OCR 실패 시 완료하지 않습니다. 선택 프로파일은 OCR 불가를 검토자가 명시 승인한 경우에만 경고와 함께 완료할 수 있습니다. 관련 폴더 추천 실패는 기본 완료 폴더 보관으로 해소할 수 있습니다.

## 4. 처리 파이프라인

1. 발견: 수동 실행 또는 감시 이벤트와 주기 재스캔을 병행합니다. 작성 완료 안정 구간과 재열기·PDF 파싱 성공을 확인합니다. 고정 대기만으로 완성을 보장하지 않습니다.
2. 등록: 파일 식별자·SHA-256, 크기·mtime, 프로파일 버전을 기록합니다. 단일 실행 잠금과 작업 임대 만료를 사용합니다. 중복 내용은 자동 삭제하지 않고 기존 처리 기록을 제시합니다.
3. 보호: 원본을 별도 보관소에 복사하고 해시를 확인합니다. 파일이 분석 중 변경되면 중단·재발견합니다.
4. 추출: 기존 텍스트층을 먼저 확인하고 이미지 전용·혼합 PDF의 필요한 페이지에 OCR를 적용합니다. 낮은 텍스트 품질은 검토 대상으로 표시합니다. OCR 산출물은 별도 임시 파일입니다.
5. 제목: 문서 내 실제 제목을 우선 사용합니다. 제목 없는 서식은 확인 가능한 문서유형·기관·날짜 조합을 제안하고 추정임을 표시합니다. 문서 날짜와 스캔 날짜를 혼동하지 않습니다. 다중 문서는 합성 제목으로 조용히 확정하지 않습니다.
6. 분류: 사용자가 선택한 폴더의 이름·설명·수동 규칙으로 후보를 구성합니다. 전체 디스크나 타겟 파일 본문을 몰래 읽지 않습니다. 기존 파일 본문 학습은 별도 범위 동의가 필요합니다.
7. 검토: LLM 자체 점수를 신뢰도로 간주하지 않습니다. 제목 근거, 규칙 적중, 후보 간 차이와 사용자 승인으로 판단합니다. 모델 출력은 데이터이며 명령·실행 코드로 해석하지 않습니다.
8. 확정: 승인한 계획과 현재 입력 해시·타겟 상태가 같은지 재검증합니다. 타겟 내부 임시 파일 → 파싱·페이지 수·출력 해시 검사 → 덮어쓰기 없는 최종 배치 → 기록 영속화를 수행합니다. 다른 볼륨은 복사·검증·원본 정리로 처리합니다.
9. 입력 정리: 위 단계와 원본 보존이 확인된 뒤에만 입력을 제거합니다. 실패·검토 대기는 입력에 남겨 미처리 건만 보이게 합니다. 입력 제거 실패는 `배치됨/입력정리대기`로 기록하고 새 결과를 또 만들지 않습니다.

제안 상태: `discovered → waiting_stable → backed_up → extracted → review_pending → approved → publishing → published → source_cleanup_pending → completed`. 오류는 단계별 `failed` 및 재시도 가능 여부로 보존합니다. 재시작 시 실제 파일·해시와 journal을 대조해 중간 상태를 복구합니다.

## 5. 안전·품질

- 이름 규칙 제안: `YYYY-MM-DD_제목__짧은ID.pdf`. 날짜 불명은 임의 날짜를 넣지 않고 설정에 따라 스캔 날짜임을 구분해 표기합니다. 개인식별정보를 파일명에 넣지 않도록 경고합니다.
- Windows 금지문자·예약이름·끝 공백/점, 경로 길이, 대소문자 충돌, macOS NFC/NFD 동치, 동명 타겟을 검사합니다. 충돌은 접미사로 해결하고 기존 파일을 덮어쓰지 않습니다.
- 경로는 승인한 루트 안으로 제한합니다. `..`, 절대경로 모델 출력, symlink/junction 탈출, 실행 중 경로 변경을 검사합니다.
- 손상·암호화·전자서명 PDF는 분리 검토합니다. 서명된 PDF를 OCR로 변형해 서명이 유지된다고 표시하지 않습니다. 처리 불가를 성공으로 위장하지 않습니다.
- PDF 처리 도구에는 시간·메모리·페이지 제한, 비권한 프로세스, 종료·취소 기능을 적용합니다. 내부 문서의 프롬프트 인젝션은 이름·분류 규칙을 바꾸지 못해야 합니다.
- SQLite와 민감한 로컬 기록은 소스 폴더 밖 사용자 앱 데이터에 둡니다. OCR 본문은 기본 로그에 저장하지 않습니다. 전송·원격 오류 수집·텔레메트리는 기본 꺼짐입니다.
- 외부 AI는 기본 비활성. 기관 정책 확인과 문서 범위·전송량·비용·수신처 동의 후에만 켭니다. API 키는 OS 자격증명 저장소를 사용합니다.
- Undo는 원본을 입력 경로에 충돌 없이 복구합니다. 최종본이 이후 변경되었으면 삭제하지 않고 수동 해결을 요청합니다. 파일별 작업은 journal로 추적하며 DB만으로 성공을 추정하지 않습니다.

## 6. 기술 방향(개발이 필요할 때)

- 핵심은 에이전트 중립 Python 라이브러리·CLI, 로컬 SQLite journal, 파일 시스템 감시+주기 스캔, 엔진 어댑터입니다. 트레이/검토 UI는 Qt 계열을 후보로 비교하되 배포·라이선스 검증 후 확정합니다.
- OCR는 OCRmyPDF+Tesseract `kor+eng`를 우선 시험합니다. Windows 네이티브 설치가 가능하므로 WSL 필수로 설계하지 않습니다. 실제 릴리스의 의존성과 깨끗한 Windows 설치를 직접 검증해야 합니다.
- PDF 래스터화·텍스트 추출·OCR의 라이선스를 구분합니다. Ghostscript를 무조건 번들하지 않으며 대체 PDF 백엔드와 배포 의무를 검토합니다.
- 향후 얇은 MCP 래퍼는 stdio+streamable-HTTP를 지원하는 방향으로 설계할 수 있습니다. 개인 폴더 정리 앱에서 원격 HTTP 서버는 기본 꺼짐이며 첫 버전에 넣지 않습니다. 원격화에는 인증·읽기/쓰기 분리·별도 위협 검토가 필요합니다.
- OS 자격증명, 파일 경로, 앱 데이터, 자동 시작은 OS 어댑터로 격리합니다. Windows 네이티브·macOS 네이티브 CI와 실제 호스트 설치 시험은 별개로 수행합니다.

### 6.1 선택 가능한 LLM 실행 경로 — 사용자 추가 요구(2026-11-04)

- LLM이 필요한 제목 추론·관련 폴더 추천은 사용자가 **Claude Code / Codex / agy(Antigravity)의 구독 로그인 CLI** 중 하나를 선택하는 경로를 지원하도록 계획합니다. 이는 개발 에이전트 선택뿐 아니라 앱의 문서 분석 실행 경로에 대한 요구입니다. 아직 연동을 구현하거나 실제 문서를 전송하지 않았습니다.
- 설정은 `LLM 사용 안 함 / 로컬 모델 / 구독 CLI / API 키`를 구분하고, 구독 CLI 선택 시 공급자와 설치된 실행 파일을 지정합니다. 구독 CLI는 사용자가 공식 로그인 절차로 인증하며, 앱이 OAuth 토큰을 추출·복제하거나 구독 인증을 임의의 API 키처럼 재사용하지 않습니다.
- 어댑터는 앱 핵심 로직과 분리합니다. 공식 비대화형 실행 인터페이스, 입력 전달 방식, 구조화 출력, 인증 상태 판별, 취소·시간 제한은 CLI별·버전별로 확인합니다. 도입 시점의 공식 문서·구독 조건에서 자동화·배포 허용 범위를 검토하고, 지원 불가 환경은 명시적으로 표시합니다. 구독 보유만으로 범용 API 사용권이나 무제한 처리량을 보장한다고 설명하지 않습니다.
- CLI 프로세스는 고정된 실행 파일과 인자 배열로 실행하고 문서 내용을 셸 명령에 보간하지 않습니다. 선택한 문서의 최소 OCR 발췌와 허용된 폴더 후보 ID만 입력하고, 출력은 제목·근거·폴더 후보 ID 등 정해진 스키마로 검증합니다. 파일 이름과 이동은 앱이 검증·승인 후 수행하며 LLM에 맡기지 않습니다.
- 일반 코딩 에이전트의 도구·MCP·플러그인·프로젝트 지침 자동 로드로 범위 밖 파일에 접근하지 않도록 해야 합니다. 파일 쓰기·셸 실행·추가 파일 읽기를 차단할 수 있는 공식 설정과 OS 격리 경계를 검증하고, 이를 보장하지 못하는 어댑터는 자동 분석에 사용하지 않습니다. 임시 작업 폴더 지정만으로 격리가 되었다고 간주하지 않습니다.
- 구독 CLI로 보낸 내용도 외부 서비스 전송입니다. 공급자별 전송 범위·로컬 대화/로그 보존 설정·기관 허용 여부를 확인하고 사용자가 명시적으로 활성화한 범위에서만 사용합니다. 기본 외부 전송 비활성 정책은 유지합니다.
- 공급자·모델·CLI 버전·작업 결과와 제한 오류를 기록하되 본문과 인증 정보는 기본 로그에 넣지 않습니다. 한도·로그인 만료·미설치·파싱 실패 시 보류하며, 유료 API 또는 다른 공급자로 조용히 우회하지 않습니다. 공급자 변경은 사용자 선택 또는 사전에 동의한 명시적 정책으로만 합니다.
- Windows와 macOS에서 각 CLI의 설치·로그인·합성 문서 분석·구조화 출력·중단·권한 제한을 따로 시험합니다. 특정 머신에서 설치되어 있다는 사실만으로 교차 플랫폼 지원을 완료했다고 보지 않습니다. OCR 텍스트층 생성은 별도 OCR 엔진 역할이며 LLM 호출 성공과 구별합니다.
- 사전조사 결과(G0): [구독 LLM CLI 어댑터 사전조사](g0/llm-cli-adapters.md) (2026-11-05 기준 macOS 시험 완료, Windows 미시험 체크리스트 수립).

## 7. 일정 제안과 게이트
